# 第 7 章：安全攻防 —— 攻击者怎么打 OAuth，我们怎么防

> 配套实验：[Demo7 - 攻防实战](../demos/07-security-attacks-defense)
> 本章是一个"靶场"：**漏洞版客户端（3000）**、**安全版客户端（3001）**、**攻击者页面（3002）**。

## 7.1 攻击一：登录 CSRF（state 缺失漏洞）

Eve 自己有合法账号 `eve`，她想让 Bob 不知不觉登录成 Eve 的身份：

1. Eve 用自己账号走一遍授权流程，拿到真实授权码 `code_EVE`；
2. 把链接 `http://localhost:3000/callback?code=code_EVE`（**没有 state**）发给 Bob；
3. Bob 点开后，漏洞版客户端不校验 state，直接拿 code_EVE 换 Token；
4. 换成功——**Bob 的浏览器里现在是 Eve 的登录态**！

> 类比：门卫不核对"预约单是谁下的"（state），谁拿着有效取件码来都能进门。

防御：发起授权时生成随机 state 存 Cookie，回调时必须比对；Eve 链接里的 state 与 Bob 浏览器里的不匹配 → 拒绝。

## 7.2 攻击二：授权码截获（PKCE 防护）

code 要经过浏览器（URL 可见于历史记录、日志、Referrer）；移动 App 的回调协议还可能被恶意 App 截获。公开客户端（SPA/移动 App）没有 client_secret，怎么防？

PKCE（RFC 7636）四步：

1. 客户端生成随机 `code_verifier`（43~128 字符）；
2. `code_challenge = BASE64URL(SHA256(code_verifier))` 随授权请求发给认证中心；
3. 认证中心把 challenge 与 code 绑定存储；
4. 换 Token 必须带原始 `code_verifier`，认证中心重算哈希比对。

> 类比：取件码公开贴在公告栏没关系——**取包裹时必须当面说"暗号"（verifier）**，
> 暗号从未离开客户端和认证中心，偷到取件码也没用。

## 7.3 其他经典攻击与防线速览

| 攻击 | 原理 | 防线 |
|------|------|------|
| 重定向劫持 | 伪造 redirect_uri 把 code 引到攻击者站点 | redirect_uri 精确匹配白名单（Demo4 已实现） |
| code 重放 | 同一 code 换两次 Token | code 一次性，用后即删（Demo4 已实现） |
| Token 泄露（XSS） | 前端 localStorage 里的 Token 被脚本偷走 | HttpOnly Cookie；短时效 Token |
| CSRF（业务请求） | 借用户 Cookie 偷偷发请求 | SameSite Cookie 属性 + CSRF Token |
| client_secret 泄露 | 前端代码里藏 secret | 公开客户端不用 secret，改用 PKCE |

## 7.4 动手实验（Demo7 靶场）

```powershell
cd I:\work-body-dir\sso-oauth-tutorial\demos\07-security-attacks-defense
npm start
```

四个服务：授权服务器 9000、漏洞版客户端 3000、安全版客户端 3001、攻击者 3002。

实验步骤：

1. 打开 `http://localhost:3002`（Eve 的攻击页面）；
2. 点击"发起攻击 → 漏洞版客户端"：Eve 已用自己账号拿到真实授权码，
   链接把你带到漏洞版回调——页面会显示 **"登录成功：eve"**！你不知不觉登录成了 Eve；
3. 点击"发起攻击 → 安全版客户端"：同样的手法，安全版因 **state 不匹配**直接拒绝 ✅；
4. 观察 3001 的终端日志：发起时带 `code_challenge`，换 Token 时带 `code_verifier`；
5. 对比 client-vuln.js 和 client-secure.js 的差异——防线就是那十几行。

## 7.5 本章小结

- state：防登录 CSRF，实现成本极低，**必须要有**；
- PKCE：公开客户端的标配，S256 防止 challenge 泄露反推 verifier；
- redirect_uri 白名单 + code 一次性 + 短时效 Token：多层防线缺一不可；
- 安全没有银弹，只有纵深防御。
