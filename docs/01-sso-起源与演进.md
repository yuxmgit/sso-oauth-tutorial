# 第 1 章：SSO 的起源与演进

> 本章目标：理解"单点登录（SSO）"到底解决什么问题，它为什么会出现，
> 以及在没有 SSO 的年代人们是怎么"将就"的。
> 配套实验：[Demo1 - 单系统登录](../demos/01-basic-session)、[Demo2 - Session 共享难题](../demos/02-session-sharing-problem)

---

## 1.1 一切从一个故事开始

Bob 在一家公司上班。2003 年，公司刚成立信息化部门，只有一套系统——**OA 办公系统**。

登录 OA 的流程非常朴素：

```
Bob 输入账号密码 ──► 服务器核对 ──► 核对通过，记住"Bob 已登录"
```

但"记住"这两个字，实现起来有大讲究。HTTP 协议是**无状态**的——
服务器处理完每个请求就忘得一干二净，下一个请求来时它根本不认识你。

> **生活类比**：HTTP 就像一个金鱼脑服务员，每上一道菜就把你忘了。
> 你每点一道菜都得重新自我介绍："我是 3 号桌的 Bob"。

于是人类发明了 **Session + Cookie** 这对黄金搭档：

1. 你第一次登录时，服务器创建一个"会话档案"（Session），存进档案柜；
2. 档案上有个编号（Session ID），服务员把编号塞给你——**这就是 Cookie**；
3. 之后你每点一道菜，都报上编号，服务员翻档案柜就知道："哦，是 3 号桌的 Bob，他今天已经点过 3 个菜了"。

```
┌──────────┐    ①登录(账号+密码)      ┌──────────────┐
│  Bob     │ ───────────────────────► │   服务器      │
│ (浏览器) │                          │  创建 Session │
│          │ ◄─────────────────────── │  存入档案柜   │
└──────────┘   ②Set-Cookie: sid=abc    └──────────────┘
     │
     │ ③之后每次请求自动携带 Cookie: sid=abc
     ▼
┌──────────┐                          ┌──────────────┐
│  Bob     │ ───────────────────────► │   服务器      │
│          │                          │  查 sid=abc   │
│          │ ◄─────────────────────── │  "是 Bob！"   │
└──────────┘                          └──────────────┘
```

这个机制**单系统内**工作得非常完美。Demo1 就带你亲手实现它。

## 1.2 好日子到头了：多系统时代的痛点

2008 年，公司业务扩张，陆续上线了 **OA、Wiki、报销系统、邮件系统**。

新的问题出现了：

**痛点 1：Bob 要记 4 套账号密码。**

每个系统各自维护用户表，各收一遍密码。Bob 要么设 4 个一样的弱密码（危险），要么天天点"忘记密码"。

**痛点 2：每个系统都要登录一遍，每天早上 10 分钟耗在登录上。**

**痛点 3：Bob 离职了，IT 要在 4 个系统里分别删除他的账号。** 忘删一个，离职员工照样登录。

**痛点 4：从安全角度，4 套系统 = 4 个密码库 = 4 个可能泄露的地方。**

这时候，大家自然想到几个"将就方案"，我们逐一分析它们为什么不行：

### 方案 A：密码同步 —— "复制粘贴密码"

所有系统共用一张用户表，或者一个系统改密码就同步给其他系统。

问题：
- 系统之间要开接口互传密码，任何一环被攻破 = 全军覆没；
- 系统越多，同步越复杂，一致性难以保证。

> **类比**：把自家钥匙复制给所有邻居，还在邻居家墙上钉一张"Bob 家钥匙备用"的纸条。钥匙多了、纸条多了，迟早出事。

### 方案 B：Cookie 共享 —— "同一域名下共用凭证"

把所有系统部署在同一个主域下：`oa.company.com`、`wiki.company.com`。
给 `.company.com` 这个域种一个共享 Cookie。

问题：
- Cookie 本身不携带"登录状态"这么复杂的语义，各系统的 Session 存储依然是分开的；
- 需要一个"公共的认证系统"来真正验证身份——但这个公共系统是谁？它发出来的凭证别的系统怎么信任？

等等——**痛点 2 的后半句其实自己给出了答案**：我们需要一个**公共的认证系统**。

### 于是 SSO 诞生了

**单点登录（Single Sign-On）** 的核心思想只有一句话：

> **把"认证"这件事从各个业务系统中抽出来，交给一个统一的认证中心。**
> Bob 只对认证中心登录一次，之后访问任何接入的系统，都由认证中心作证："这是 Bob，我认识他，放行。"

> **生活类比**：以前每栋楼（每个系统）都有自己的保安，进门都要登记身份证。
> 现在园区统一办了**门禁卡**（认证中心发的凭证），各楼保安只认卡不认人——刷卡进楼，一次办卡，处处通行。

## 1.3 SSO 的经典架构

```
                    ① Bob 登录认证中心（只登一次）
┌──────────┐ ─────────────────────────► ┌────────────────┐
│   Bob    │                            │   认证中心      │
│ (浏览器) │ ◄───────────────────────── │  AuthServer    │
└──────────┘  ② 发给 Bob 一张"全局凭证"  └───────┬────────┘
     │                                          │
     │ ③访问 App A / App B 时，                  │ ⑤各应用拿凭证
     │  先跳到认证中心换"局部凭证"                │   来认证中心验真伪
     ▼                                          ▼
┌──────────┐   ┌──────────┐   ┌──────────┐ ┌──────────┐
│  App A   │   │  App B   │   │  App C   │ │ 报销系统  │
│ (Wiki)   │   │  (OA)    │   │ (Jira)   │ │          │
└──────────┘   └──────────┘   └──────────┘ └──────────┘
        全部信任同一个认证中心
```

注意两个关键设计：

1. **凭证分两级**：
   - **全局凭证**：Bob 与认证中心之间的会话（比如存在认证中心域名下的 Cookie）；
   - **局部凭证**：认证中心发给某个具体应用的"门票"（票据）。
2. **各应用不认人，只认票据**：应用拿到局部凭证后，还要**回认证中心验一下真伪**（服务端对服务端的校验，不走浏览器），确认无误才建立自己的登录会话。

这两条设计贯穿后面所有方案：CAS 的 TGT/ST、OAuth2 的授权码/AccessToken、OIDC 的 ID Token——**万变不离其宗**。

## 1.4 一个最朴素的 SSO 轮廓（先睹为快）

我们用伪代码描绘一下最简单的 SSO 流程（后面章节会逐步实现它）：

```
Bob 访问 App A（未登录）
  └─► App A 发现没登录，302 跳转：认证中心?redirect=AppA
        └─► 认证中心让 Bob 登录
              └─► 登录成功，认证中心建立全局会话，302 回跳 AppA 并附带 ticket
                    └─► App A 拿 ticket 找认证中心验真伪
                          └─► 验证通过，App A 建立 Bob 的局部会话 ✅

Bob 访问 App B（未登录）
  └─► App B 302 跳转：认证中心?redirect=AppB
        └─► 认证中心一看：Bob 已有全局会话（全局 Cookie 还在）
              └─► 不用再登录！直接发 ticket 回跳 App B ✅   ← 这就是"单点"
```

**"单点"的精髓就在倒数第二步**：第二次访问时，因为认证中心的全局会话还在，
用户完全无感知，自动完成登录。

## 1.5 动手实验

### 实验 1：感受 Session + Cookie（Demo1）

```powershell
cd I:\work-body-dir\sso-oauth-tutorial\demos\01-basic-session
npm start
```

浏览器打开 `http://localhost:3000`，按页面提示操作：

1. 访问 `/profile` 会发现"未登录，请先登录"；
2. 去登录页输入 `bob / 123456`；
3. 再访问 `/profile`，能看到你的会话信息；
4. 打开开发者工具（F12）→ Application → Cookies，观察 `sid`；
5. 点"退出登录"，Cookie 被清除，再访问 `/profile` 又要登录了。

**思考题**：退出登录时，服务器删除了什么？浏览器删除了什么？
（答案：服务器删除了档案柜里的 Session 记录；浏览器清除了 sid Cookie。两边都删，缺一不可。）

### 实验 2：见证 Cookie 的"域边界"（Demo2）

```powershell
cd I:\work-body-dir\sso-oauth-tutorial\demos\02-session-sharing-problem
npm start
```

这个 Demo 会同时启动两个应用：

- 应用 A：`http://localhost:3000`（OA 系统）
- 应用 B：`http://localhost:3001`（Wiki 系统）

按提示分别在两个应用登录，你会发现：

1. 在应用 A 登录后，应用 B **完全不认识你**——两个应用的档案柜（Session 存储）是分开的；
2. 即使浏览器把 A 发的 Cookie 也发给了 B（Cookie 不区分端口！），B 也查无此人。

> **注意这个反直觉细节**：Cookie 是按"域"隔离的，不按端口。localhost:3000 和 localhost:3001 共享 Cookie 存储。但 Cookie 里只有一个无意义的随机串，B 的档案柜里没有这条记录，所以依然"未登录"。这正是第 1.2 节"方案 B"失败的原因——共享 Cookie 不等于共享会话。

这个实验让你亲身感受"**为什么需要 SSO**"——带着这个痛点，我们进入第 2 章，
看看人类是怎么设计出 OAuth 这套优雅协议的。

---

## 1.6 本章小结

- HTTP 无状态 → 需要 Session + Cookie 来"记住"登录状态；
- 多系统时代：重复登录、重复维护用户、重复的安全风险；
- 密码同步和 Cookie 共享都是死路，正确答案是把认证集中到**认证中心**；
- SSO 的核心：**全局凭证 + 局部票据 + 服务端验票**。
