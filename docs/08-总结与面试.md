# 第 8 章：总结与面试 —— 从知识到工程决策

> 全教程收官章：把 7 章内容收敛成"选型决策表"和"面试答题框架"。

## 8.1 全景回顾：一条主线

```
HTTP 无状态 ──► Cookie+Session 记住你 ──► 多系统重复登录的痛
     ──► 认证集中到认证中心（SSO）──► 跨系统授权需求（OAuth）
     ──► 协议安全持续加固（state/PKCE/短Token）──► 身份标准化（OIDC）
```

所有方案都在回答同一对问题：
- **认证（Authentication）**：你是谁？—— SSO、CAS、SAML、OIDC、Session/JWT
- **授权（Authorization）**：你被允许做什么？—— OAuth2、RBAC、scope

## 8.2 方案选型决策表

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 公司内网多系统统一登录 | OIDC（如 Keycloak/Auth0）或 CAS | 管认证、生态成熟、标准协议 |
| 面向 C 端的第三方登录 | OAuth2 授权码 + PKCE + OIDC | 微信/Google/GitHub 均支持，安全标配 |
| 纯前端 SPA / 移动 App | 授权码 + PKCE（绝不用 Implicit） | 无 secret，靠 PKCE 防 code 截获 |
| 服务对服务（无用户） | 客户端凭证模式 | 简单、无浏览器环节 |
| 传统企业与 Salesforce/AD 对接 | SAML 2.0 | 对方生态就是 XML 世界 |
| 需要立即踢人/强注销 | Session（集中存储） | 服务端可随时删会话 |
| 微服务间传递身份 | 短 JWT + Refresh Token | 无状态验签，天然跨服务 |
| 遗留自研 SSO | 建议 CAS 或 OIDC 改造 | 自造轮子的协议难以审计 |

## 8.3 面试高频题（附答题要点）

**Q1：Session 和 JWT 的区别？怎么选？**
答：Session 服务端存状态（可控可注销，集群需集中存储）；JWT 客户端自持（无状态可扩缩容，难吊销）。
选型：需要强注销/踢人选 Session；微服务/跨服务传身份选 JWT；主流组合是"短 JWT + 可吊销的 Refresh Token"。

**Q2：OAuth2 授权码模式为什么先发 code 再换 Token，而不是直接发 Token？**
答：code 经过浏览器（不可信区域），Token 只在服务器间流动（可信区域）。code 一次性、短时效、
换 Token 需 client_secret——即使 code 被截获也换不到 Token。

**Q3：state 和 PKCE 分别解决什么问题？**
答：state 防 CSRF（回调必须携带客户端预置的随机数，保证"回调对应本次发起"）；
PKCE 防授权码截获（公开客户端用 challenge/verifier 证明"换 Token 的还是发起授权的那个客户端"）。

**Q4：OAuth2 是认证协议吗？OIDC 补了什么？**
答：不是，OAuth2 只管授权。OIDC 在其上加 openid scope 和标准化的 ID Token（JWT，
含 iss/sub/aud/exp/nonce），客户端本地验签即可确认用户身份，nonce 防重放。

**Q5：JWT 被签发后如何"注销"？**
答：JWT 本身无法吊销。方案：① 短有效期降低风险窗口；② Refresh Token 存服务端可随时吊销；
③ 黑名单（把 jti 加 Redis，代价是回到"有状态"）；④ 网关层统一校验黑名单。

**Q6：CAS 的 TGT 和 ST 分别是什么？为什么 ST 要一次性？**
答：TGT 是用户与 CAS 的全局会话；ST 是发给具体应用的一次性票据。ST 一次性 + 实时回调验票
防票据重放；应用验证通过后建立自己的局部会话。

**Q7：SSO 单点登出（SLO）为什么难？**
答：各应用局部会话独立，认证中心无法直接清除它们。需要协议级通知（SAML LogoutRequest、
OIDC Back-Channel Logout），工程上常退化为"认证中心登出 + 应用会话过期"。

**Q8：重定向劫持怎么防？**
答：redirect_uri 必须与注册白名单精确匹配（不做前缀/子串匹配），拒绝通配符；配合 state 双保险。
