# 第 10 章（进阶专题）：JWT 和 OAuth 到底有什么区别？

> 这是面试和日常讨论中**最容易混淆**的一对概念。本章把它们彻底掰开讲清楚。
> 前置知识：第 3 章（JWT）、第 4 章（OAuth2）。

## 10.1 一句话结论（先记住这个）

**JWT 和 OAuth 根本不是同一层面的东西，不存在"二选一"：**

```
JWT  = 一种"令牌的格式"        —— 回答"凭证长什么样、怎么自证"
OAuth = 一套"发凭证的流程"     —— 回答"凭证怎么签发、怎么授权、谁来批准"
```

> 类比：
> - **JWT** 是**车票的样式**——带防伪二维码、写着你座位号、检票机扫码即验；
> - **OAuth** 是**整套售票制度**——你先去售票窗口（认证中心）买票，
>   检票员（资源服务器）按制度验票，铁路局（授权服务器）规定谁能上哪趟车。
>
> 问"JWT 和 OAuth 有什么区别"，就像问"车票和售票制度有什么区别"——
> 车票可以由任何机构按任何样式印制（不一定走铁路售票制度），
> 而售票制度发出来的票也不一定是这种样式（可能是不记名的纸质票）。

## 10.2 各自到底"是"什么

### JWT：一种令牌格式（RFC 7519）

JWT 定义的是**凭证本身的编码方式**——三段式字符串：

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJib2IiLCJyb2xlIjoidXNlciJ9 . 4fQ3xK...
     Header（怎么签）         Payload（写了什么）          Signature（防伪印）
```

它的全部职责：

- **自包含**：用户信息（claims）直接写在 Payload 里，验证方不需要查数据库；
- **防篡改**：签名保证内容没被动过；
- **可离线验证**：持有密钥/公钥的任何服务都能独立验真。

注意：JWT **没有规定**"谁在什么流程下发它、发给谁、权限怎么管理"——
这些都不归它管。你在自己系统里登录后手写一个 JWT 发出去，也是合法用法（Demo3 就是这样）。

### OAuth 2.0：一个授权框架（RFC 6749）

OAuth 定义的是**凭证的签发流程和角色关系**——它不关心凭证长什么样：

```
四个角色：
  资源所有者（用户）─── "我允许这个应用替我读我的资料"
  客户端（第三方应用）── "我想拿到访问用户资源的凭证"
  授权服务器 ────────── "经用户同意后，我把凭证发给你"
  资源服务器 ────────── "凭证给我看一眼，验过才让你访问"
```

它规定的是**这些角色之间怎么互动**：

- 用户怎么表达"同意"（授权端点）；
- 客户端怎么拿到凭证（授权码模式、客户端凭证模式等）；
- 凭证怎么换新的（Refresh Token）；
- 安全防线怎么布（redirect_uri 白名单、state、PKCE）。

注意：OAuth 2.0 **没有规定**凭证的内容和编码——
它的 access_token 可以是 JWT，也可以是一串不透明的随机字符，协议本身不在乎。

## 10.3 维度对比表（面试可直接背）

| 维度 | JWT | OAuth 2.0 |
|------|-----|-----------|
| 本质 | **令牌格式**（数据结构 + 签名规范） | **授权流程**（角色 + 交互协议） |
| 解决的问题 | "凭证如何自证、如何防篡改" | "如何安全地把授权委托给第三方" |
| 谁定义的细节 | Payload 里放什么、怎么签名 | 授权端点、令牌端点、回调、scope |
| 有没有"用户同意"环节 | 没有，签发完全由实现者自己决定 | ✅ 核心就是用户同意（consent） |
| 有没有"第三方"概念 | 没有，谁签谁验都行 | ✅ 客户端/授权服务器/资源服务器是协议的一部分 |
| 验证方式 | 本地验签（不联网、无状态） | 资源服务器与授权服务器配合（可联网校验） |
| 典型载体 | 就是令牌本身 | access_token / refresh_token / id_token |
| 能否单独使用 | ✅ 能（单系统自签自验，Demo3） | ✅ 能（access_token 可以是不透明串） |
| 回答"你是谁" | 能（Payload 里有 sub） | 严格说不能——OAuth 只管授权，认证交给 OIDC |

## 10.4 它们如何配合：三层关系图

实践中最常见的架构是"**OAuth 负责流程，JWT 负责凭证**"：

```
┌──────────┐  ①登录/授权   ┌──────────────┐
│   用户    │ ───────────► │  授权服务器    │
└──────────┘              │ (Auth Server) │
                          │  签发 access_token
                          │  ┌─────────────────────────┐
                          │  │ 这个token本身用JWT格式编码 │  ← JWT 出场
                          │  └─────────────────────────┘
                          └──────┬───────────────────┘
                                 │ ②下发令牌
                                 ▼
┌──────────┐  ③带着token调API ┌──────────────┐
│  客户端   │ ──────────────► │  资源服务器    │
└──────────┘                 │ 本地验JWT签名  │  ← JWT 再次出场（验证）
                             │ 检查scope/exp │
                             └───────────────┘
```

三个关键结论：

1. **OAuth 里的 access_token 不一定是 JWT**——可以是不透明串（opaque token），
   资源服务器每次拿它去授权服务器换用户信息（introspection，内省）；
2. **JWT 不需要 OAuth 也能用**——单系统登录自己签自己验（Demo3）；
3. **两者搭配是最主流的工程实践**——OAuth 管安全和授权流程，JWT 管"资源服务器零成本验证"。

## 10.5 实例对比：三段真实可跑的例子

### 实例 A：只有 JWT，没有 OAuth（Demo3 的世界）

单系统，自己登录自己验证：

```powershell
cd I:\work-body-dir\sso-oauth-tutorial\demos\03-jwt-login
npm start
```

```powershell
# 登录 → 服务端直接签发 JWT
curl.exe -X POST http://localhost:3000/login -d "username=bob&password=123456"
# 返回：eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJib2Ii...（三段式）

# 验证：资源端点只认签名，不认任何"授权流程"
curl.exe "http://localhost:3000/profile?token=eyJhbGciOiJIUzI1NiJ9..."
```

特征：**没有授权服务器、没有用户同意页、没有第三方应用**。
这就是"纯 JWT"，它甚至算不上一个协议交互——只是一个带签名的字符串。

### 实例 B：OAuth 2.0 流程 + JWT 格式的 access_token（Demo4 的世界）

第三方应用要代表用户访问资源：

```powershell
cd I:\work-body-dir\sso-oauth-tutorial\demos\04-oauth2-authorization-code
npm start   # 三个服务：客户端3000 / 授权服务器9000 / 资源服务器9001
```

浏览器打开 `http://localhost:3000`，登录并同意后，看客户端终端日志：

```
[token] POST /token  grant_type=authorization_code
[token] 响应: {
  "access_token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJib2IiLCJzY29wZSI6InByb2ZpbGUi...",  ← JWT 格式
  "token_type": "Bearer",
  "expires_in": 3600
}
```

```powershell
# 客户端拿这个 JWT 去调资源服务器
curl.exe -H "Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJib2Ii..." http://localhost:9001/api/userinfo
```

和实例 A 的区别：

| 环节 | 实例 A（纯 JWT） | 实例 B（OAuth + JWT） |
|------|-----------------|----------------------|
| 有没有第三方应用 | 没有 | 有（客户端拿"用户同意"换 token） |
| 用户要不要表达同意 | 不需要（登录即登录） | 需要（consent 页） |
| token 是发给谁的 | 用户自己的浏览器 | **第三方应用**（代表用户访问） |
| 谁验证 token | 本系统自己 | 独立的资源服务器 |
| 有没有 scope | 想写就写，无约束 | 有明确含义：授权范围 |

### 实例 C：OAuth 2.0 流程 + 不透明 token（没有 JWT 的 OAuth）

OAuth 完全可以不用 JWT。把 Demo4 的 `/token` 改成返回随机串：

```
[token] 响应: {
  "access_token": "at_9f8e7d6c5b4a3210fedcba9876543210",   ← 随机串，无任何含义
  "token_type": "Bearer"
}
```

资源服务器验票方式变为"**内省**"（introspection）：

```
资源服务器 ── POST /introspect  token=at_9f8e... ──► 授权服务器
资源服务器 ◄── { "active": true, "sub": "bob", "scope": "profile" } ──
```

代价：每次请求都要联网问一次授权服务器（多一次网络往返）。
好处：**吊销立竿见影**——授权服务器删掉这条记录，令牌当场失效（JWT 做不到）。

> 所以工程上常这样权衡：**需要高性能、无状态验证 → JWT；需要强吊销控制 → 不透明 token**。
> 混合方案也常见：短时效 JWT（快）+ 可吊销的不透明 Refresh Token（可撤销）。

## 10.6 面试高频问答

**Q1："项目里用的是 JWT 还是 OAuth？"这个问法对吗？**
答：不对，两者不是互斥选项。正确的问法是：
"认证方案是什么（Session/JWT）？有没有走 OAuth 授权流程（自建登录还是接入第三方/统一认证中心）？
access_token 用的什么格式（JWT / 不透明串）？"
一个项目完全可以是"OAuth 流程 + JWT 格式令牌"或"OAuth 流程 + 不透明令牌"或"纯 JWT、无 OAuth"。

**Q2：为什么 OAuth 不直接规定用 JWT？**
答：OAuth 诞生（2010 年 RFC 6749）早于 JWT 的普及（RFC 7519，2015 年）；
而且 OAuth 刻意保持"令牌格式无关"——不同场景诉求不同：
有的要可吊销（不透明串），有的要可离线验证（JWT），有的要加密（JWE）。
把格式写死会失去灵活性。

**Q3：JWT 能实现第三方登录吗？**
答：单靠 JWT 不能。"第三方登录"的本质是**授权委托**——
第三方应用需要征得用户同意、并从可信方获取凭证，这正是 OAuth 的流程职责。
JWT 只能在流程末端作为凭证载体出现（配合 OIDC 的 ID Token）。

**Q4：JWT 和 OAuth 各自的安全性短板是什么？**
答：JWT：签出难收回（吊销困难）、Payload 明文（需配 JWE）、算法混淆风险（alg=none 攻击）；
OAuth：实现复杂度高，redirect_uri/state/PKCE 等安全环节一旦实现不严就有漏洞（见第 7 章 Demo7）。

**Q5：一句话总结两者关系？**
答：**OAuth 是"怎么发证、怎么授权"的制度，JWT 是"证件本身的一种样式"；
制度可以发任何样式的证件，样式的证件也可以由任何机构发放。**

## 10.7 场景选型速查

| 你的场景 | 需要OAuth？ | 需要JWT？ | 说明 |
|---------|------------|-----------|------|
| 单体应用，用户自己登录 | 不需要 | 可选 | Session 或 JWT 都行（Demo1 vs Demo3） |
| 微服务间传递用户身份 | 不需要（内部直连） | ✅ 推荐 | 网关验一次，下游传递（Demo3 思路） |
| 允许第三方应用访问用户数据 | ✅ 必须 | 可选 | OAuth 授权码模式；token 格式自选 |
| 接入微信/GitHub 登录 | ✅ 必须 | 由对方决定 | 你是客户端，token 是对方发的 |
| 公司内多个系统统一登录 | 建议（OIDC） | 可选 | 本质是 OAuth + ID Token（Demo6） |

## 10.8 本章小结

- **JWT 是格式，OAuth 是流程**——一个管"凭证长什么样"，一个管"凭证怎么发"；
- JWT 可以脱离 OAuth 存在（单系统自签自验）；OAuth 也可以不用 JWT（不透明 token + 内省）；
- 最主流的工程实践是两者配合：**OAuth 管授权与安全流程，JWT 管资源服务器的高效验证**；
- 判断项目方案时，请分三个问题问：认证用什么（Session/JWT）？授权走不走 OAuth？令牌什么格式（JWT/JWE/不透明）？
