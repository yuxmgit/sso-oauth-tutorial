# 第 9 章（进阶专题）：JWE —— 当令牌里的内容不能给别人看

> 前置知识：第 3 章 Session 与 JWT。
> 本章 9.4 ~ 9.10 是**零基础保姆级加餐**：从"钥匙是什么"讲到"每一步谁手里有什么"，
> 完全不要求你懂密码学，跟着故事走即可。

## 9.1 一个常见误解：JWT 是"加密"过的

很多同学第一次见到 JWT 会这样想：

> "这一大串乱码，肯定是加密的，别人看不懂。"

**错。** 随便拿一个 JWT 到任何在线解码器粘一下：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJib2IiLCJwaG9uZSI6IjEzODAwMDAxMjM0In0.xxxxx
     ↓ base64url 解码（不需要任何密钥）
{"alg":"HS256","typ":"JWT"}
{"sub":"bob","phone":"13800001234"}     ← 手机号清清楚楚
```

JWT（严格说是 **JWS**，JSON Web Signature）只做了两件事：
1. **Base64url 编码** —— 编码不是加密，只是换个写法；
2. **签名** —— 防止别人偷偷改动内容。

它保护的是**完整性**（没被改），**不保护机密性**（不被看）。

> 类比：**明信片**。邮路上谁都能读，但谁要是涂改，收件人一看笔迹/邮戳就知道被动过手脚。

### 什么时候这是灾难？

| 场景 | 泄露后果 |
|------|---------|
| Token 里放了手机号、身份证、住址 | 个人隐私泄露，违反《个人信息保护法》 |
| 放了内部权限清单、风控标记 | 攻击者据此精准构造越权请求 |
| 放在 URL / Referrer / 浏览器历史里 | 日志、代理、截图都可能留存明文 |
| 跨组织传递（合作方、子公司） | 对方可读到你不想共享的字段 |

这时你需要的不是"再签一次名"，而是**真的加密**：**JWE（JSON Web Encryption，RFC 7516）**。

> 类比：**上锁的信封**。锁着送出去，只有收件人有钥匙；路上被拆开，封条（认证标签）也会露馅。

## 9.2 JWS 与 JWE 一张表看懂

| 维度 | JWS（JWT 常用形态） | JWE |
|------|---------------------|-----|
| 目标 | 防篡改（完整性） | 防偷看（机密性）+ 防篡改 |
| 外观 | 3 段：`header.payload.signature` | **5 段**：`header.encryptedKey.iv.ciphertext.tag` |
| 内容 | base64url 明文，人人可读 | AES 密文，无私钥不可读 |
| 谁能验证/解密 | 所有人（验签只需公钥） | 只有持有解密私钥/对称密钥的一方 |
| 典型标识 | Header `alg=HS256/RS256/ES256` | Header `alg + enc`，如 `RSA-OAEP-256 + A256GCM` |
| 性能 | 快 | 慢一些（多了加解密与密钥包裹） |

一句话：**JWS 让内容"改不了"，JWE 让内容"看不见"。**

## 9.3 拆开 JWE：五段各是什么

```
BASE64URL(Header) . BASE64URL(EncryptedKey) . BASE64URL(IV) . BASE64URL(Ciphertext) . BASE64URL(Tag)
```

以 Demo8 的 `RSA-OAEP-256 + A256GCM` 为例：

```
eyJhbGciOiJSU0EtT0FFUC0yNTYiLCJlbmMiOiJBMjU2R0NNIn0
    ↓ 解码
{"alg":"RSA-OAEP-256","enc":"A256GCM","typ":"JWT","cty":"JWT","kid":"demo-key"}
```

| 段 | 名称 | 作用 | 类比 |
|----|------|------|------|
| 1 | **Header** | 声明用什么算法（alg 包密钥、enc 加密内容），可放 kid | 信封上写的"投递方式" |
| 2 | **EncryptedKey** | 用接收方公钥加密后的**一次性对称密钥 CEK** | 装在信封里的一把一次性钥匙 |
| 3 | **IV** | AES-GCM 的初始化向量（12 字节随机） | 每封信不同的"乱码种子" |
| 4 | **Ciphertext** | 真正的业务数据被 AES 加密后的结果 | 信纸正文（已上锁） |
| 5 | **Tag** | 认证标签，校验密文与 Header 是否被改 | 一次性封条 |

### 为什么不直接用 RSA 加密数据？

因为 RSA 又慢、又有长度限制（2048 位最多加密约 190 字节）。
所以 JWE 使用**混合加密**：

1. 随机生成一把 **CEK**（Content Encryption Key，32 字节）；
2. 用**快**的对称算法（AES-GCM）加密大块数据；
3. 用**安全**的非对称算法（RSA-OAEP / ECDH-ES）只加密这把小钥匙。

> 这就是 HTTPS、PGP、Signal 都在用的同一套路：**用非对称钥匙送对称钥匙**。

## 9.4 零基础加餐①：三个角色，四把"钥匙"

### 先讲个故事

Bob 在"发证中心"登录后，发证中心要给他签发一张令牌，但令牌里写着他的**手机号**。
这张令牌稍后要交给"资料库"（资源服务器）验证并读取。

路上令牌会经过：浏览器地址栏、网关、日志、可能有攻击者 Eve。

问题来了：**怎么保证只有"资料库"能看懂内容，而路上的其他人只能干瞪眼？**

答案是：**给资料库配一套锁和钥匙**。这套东西一共四样，请逐个记牢：

### 四样东西的身份证

| 名称 | 谁生成 | 谁保存 | 能否在网上传输 | 作用 | 泄露后果 |
|------|--------|--------|----------------|------|---------|
| **公钥**（Public Key） | 资料库（接收方）生成 | 谁都能存，可公开 | ✅ 可以，越公开越好 | 相当于"投递口"，用来**加密** | 没啥损失（本来就是公开的） |
| **私钥**（Private Key） | 资料库（接收方）生成 | **只有资料库自己** | ❌ **绝对不能** | 相当于"取件钥匙"，用来**解密** | 💥 所有历史令牌全部可被解开 |
| **CEK**（内容密钥，32 字节随机数） | 发证中心每次临时生成 | 不长期保存，用完即丢 | ⚠️ 只能**加密后**跟着令牌走 | 用来加密真正的业务数据 | 单次令牌内容泄露（影响限于一次） |
| **IV**（12 字节随机数）+ **Tag**（16 字节） | 发证中心每次临时生成 | 不保存，随令牌一起走 | ✅ 可以（公开也无所谓） | IV=加密的"乱码种子"；Tag=防拆封条 | 不致命，但 IV 重复使用会致命 |

> 一句话记忆：**公钥可以满天飞，私钥只能锁保险柜，CEK 是一次性钥匙，IV 是每封信都要换的种子。**

### 三种加密方式，用生活场景讲透

**① 对称加密：一把钥匙开一把锁**

你和对方**各拿一把一模一样的钥匙**，用它锁箱子、也用它开箱子。

- ✅ 优点：快，加密大量数据毫无压力（AES 就是干这个的）；
- ❌ 死穴：**钥匙怎么安全地送到对方手里？** 寄过去怕被截，见面交又太麻烦。

**② 非对称加密：信箱投递口 + 取件钥匙**

- **公钥 = 信箱的投递口**：装在门外，谁都能往里塞信；
- **私钥 = 取件的钥匙**：你自己收着，只有你能打开信箱取信。

- ✅ 优点：不用先"送钥匙"，公钥直接公开发给全世界都行；
- ❌ 缺点：慢，而且一次能装的量很小（RSA-2048 一次最多约 190 字节）。

**③ 混合加密：用投递口，寄一把一次性钥匙**

JWE 的选择——两者结合，各取所长：

```
第 1 步：随便造一把一次性钥匙（CEK，32 字节）
第 2 步：把这把钥匙从对方的"投递口"（公钥）塞进去 → 只有对方能取出来
第 3 步：用这把一次性钥匙，把大箱子（业务数据）锁上（AES 加密）
第 4 步：把"上锁的箱子"和"塞进投递口的钥匙"一起寄过去
```

这就是 JWE 五段里 `EncryptedKey` 段存在的全部意义：**它是被公钥加密过的 CEK**。

### 一个必须纠正的直觉

| 常见错误说法 | 正确说法 |
|-------------|---------|
| "公钥加密，公钥也能解密" | 公钥加密的数据只有**对应私钥**能解 |
| "双方都要有私钥" | 只有**接收方**有私钥；发送方只要有对方公钥 |
| "私钥加密、公钥解密" | 那是**签名**（JWS）；加密是反过来：**公钥加密、私钥解密** |
| "JWE 一定用 RSA" | 也可以用 `ECDH-ES`（协商）或 `dir`（共享对称密钥） |

## 9.5 零基础加餐②：加密侧的 10 步（发证中心在做什么）

假设发证中心要为 Bob 签发一条含手机号的令牌，接收方是资料库。
每一步都写清楚：**谁做、手上有什么、产出什么、为什么这么设计**。

> 你可以在 Demo8 的 `token.js` 里逐行对照 `encryptJwe()`，代码和下面 10 步一一对应。

**第 1 步：准备业务数据**
- 谁：发证中心
- 手上：Bob 的用户信息
- 产出：一段 UTF-8 文本，例如
  `{"sub":"bob","name":"Bob 打工人","phone":"13800001234"}`（约 100 字节）
- 为什么：加密的对象最终是"字节流"，先序列化成 JSON 字符串

**第 2 步：造一把一次性钥匙 CEK**
- 谁：发证中心
- 手上：一个随机数生成器（`crypto.randomBytes(32)`）
- 产出：**32 字节**的随机 CEK（256 位）
- 为什么：每次签发都用**新的** CEK。这样即使某一次被攻破，也只影响这一张令牌

**第 3 步：写"信封说明"Header，并编码**
- 谁：发证中心
- 产出：`{"alg":"RSA-OAEP-256","enc":"A256GCM","kid":"demo-key"}`，base64url 后得到第 1 段
- 为什么：告诉接收方"钥匙是怎么包的、内容是怎么锁的、用哪把私钥"
- 关键：这段**明文可见**，所以绝不能把秘密写进 Header

**第 4 步：用资料库的公钥，加密 CEK**
- 谁：发证中心（用的是**资料库的公钥**，公开可查）
- 手上：资料库公钥 + CEK
- 产出：`EncryptedKey` 段，**256 字节**（RSA-2048 的输出长度固定）
- 为什么：这是全流程唯一"必须靠非对称"的一步，只加密 32 字节，开销可接受
- 注意：**发证中心没有、也不需要资料库的私钥**

**第 5 步：生成 IV（每封信不同的种子）**
- 谁：发证中心
- 手上：随机数生成器
- 产出：**12 字节**随机 IV
- 为什么：AES-GCM 要求"同一把钥匙下 IV 绝不重复"。每次随机会自然满足
- 后果警示：IV 复用会让攻击者能推导出明文、甚至伪造密文——这是最容易翻车的地方

**第 6 步：初始化 AES-GCM 加密器**
- 谁：发证中心
- 手上：CEK + IV
- 代码：`crypto.createCipheriv('aes-256-gcm', cek, iv)`
- 为什么：这是"用一次性钥匙锁箱子"的动作，速度极快

**第 7 步：把 Header 绑定为 AAD（防拆信封说明）**
- 谁：发证中心
- 代码：`cipher.setAAD(Buffer.from(headerB64, 'ascii'))`
- 为什么：让 Header 也进入"防篡改"范围。否则攻击者可以把 `alg` 或 `kid` 换掉，诱导接收方用错密钥

**第 8 步：加密业务数据**
- 谁：发证中心
- 产出：`Ciphertext` 段（约 100 字节，和原文长度相同）
- 注意：加密后**长度不会暴涨**（这点和 RSA 不同），膨胀主要来自 base64 编码（+33%）

**第 9 步：取出认证标签 Tag**
- 谁：发证中心
- 代码：`cipher.getAuthTag()` → **16 字节**
- 为什么：AES-GCM 是"带封条的锁"。谁改了密文，接收方一验封条就会失败

**第 10 步：拼成 5 段，交给浏览器/网络**
- 谁：发证中心
- 产出：`header.encryptedKey.iv.ciphertext.tag`，每段 base64url
- 此时发证中心可以**立刻销毁 CEK 和 IV**（它们已经"装进信里"了）

> 加密侧一句话总结：**造钥匙 → 锁进投递口 → 用钥匙锁箱子 → 贴封条 → 寄出。**

## 9.6 零基础加餐③：解密侧的 8 步（资料库在做什么）

**第 1 步：拆成 5 段**
数一数是不是 5 段，不是就直接拒绝（可能是被截断或伪造格式）。

**第 2 步：读 Header，做算法白名单校验**
- 只接受 `alg=RSA-OAEP-256`（或你允许的值）与 `enc=A256GCM`；
- 根据 `kid` 找到本机对应的私钥；
- 为什么：防止攻击者用弱算法（如 `none`、`RSA1_5`）降级攻击。

**第 3 步：用私钥解开 EncryptedKey，得到 CEK**
- 代码：`crypto.privateDecrypt(...)`
- 失败说明：这段密文**不是用我的公钥加密的**（不是给我的令牌），直接拒绝。

**第 4 步：初始化 AES-GCM 解密器**
- 代码：`createDecipheriv('aes-256-gcm', cek, iv)`
- 此时还没验证内容真伪，只是准备好工具。

**第 5 步：把 Header 作为 AAD 喂进去**
- 必须用**收到的 Header 原文**（base64url 字符串），不能自己重新拼一个。

**第 6 步：贴上 Tag**
- 代码：`decipher.setAuthTag(tag)`

**第 7 步：解密并校验封条**
- `decipher.update()` + `decipher.final()`
- 只要有一处不一致（密文被改、Header 被改、Tag 被改），`final()` 会**抛异常**；
- 关键安全观：**宁可报错，也绝不返回"半真半假"的数据**。

**第 8 步：得到明文，再做业务校验**
- `JSON.parse` 后检查 `exp`（是否过期）、`aud`（是不是发给我的）、`scope`（权限够不够）；
- 为什么：解密只证明"内容没被改且是给我的心"，**不代表内容仍然有效**。

> 解密侧一句话总结：**拆信 → 验投递方式 → 取钥匙 → 开箱 → 验封条 → 查验有效期。**

## 9.7 全程透明度表：谁在什么时候看到了什么

这是理解 JWE 最快的一张表。**请重点看"私钥"和"CEK"两列。**

| 角色 | payload 明文 | CEK（一次性钥匙） | 资料库私钥 | 公钥 | 能改内容吗 |
|------|-------------|------------------|-----------|------|-----------|
| Bob（数据主人） | ✅ 自己的信息 | ❌ | ❌ | ❌ | — |
| 发证中心 | ✅（它写的） | ✅ 造出来、用完即丢 | ❌ **没有** | ✅ | ✅（它就是签发方） |
| 网络/网关/日志 | ❌ 只有密文 | ❌（被公钥包着） | ❌ | ✅ | 能改，但一改就验不过 |
| 攻击者 Eve | ❌ | ❌ | ❌ | ✅ | 能改、能重放，但**解不开也伪造不了** |
| 资料库（接收方） | ✅ 解密后可见 | ✅ 解出来（临时） | ✅ **唯一持有** | ✅ | ❌（没有签名密钥就伪造不了来源） |

### 攻击者 Eve 到底能做到什么？

| Eve 的动作 | 结果 |
|-----------|------|
| 抓包拿走整串 JWE | 只能看到 5 段乱码和算法名，读不到手机号 |
| 修改 Ciphertext 里一个字节 | 接收方 Tag 校验失败，解密被拒（Demo8 可点按钮验证） |
| 修改 Header（如换 alg / kid） | AAD 校验失败，同样被拒 |
| 把令牌原样重放 | ✅ **能成功**！所以必须靠 `exp` 短时效、`jti` 防重放、绑定受众等机制兜底 |
| 自己造一个"合法" JWE | ❌ 没有资料库公钥之外的私钥也能加密，但**内容来源无法证明**；所以"只加密不签名"时不可追责 |

> 最后一行很重要：**JWE 解决"看不见"，不解决"谁写的"。** 要两者兼得，见 9.14 的嵌套令牌。

## 9.8 密钥到底存在哪里？（存储详解）

先记住一条铁律：**密钥不是"配置"，而是"资产"。配置可以截图发群，密钥不行。**

### 三类密钥的存放位置对照表

| 密钥 | 开发环境（学习/Demo） | 生产环境（真实项目） | 谁有权访问 |
|------|---------------------|--------------------|-----------|
| **公钥** | 直接写在代码/配置文件里 | 从 JWKS 端点拉取并缓存 | 全世界（无所谓） |
| **私钥** | 启动时内存生成，进程退出即消失（Demo8 做法） | **KMS / HSM 托管**，或容器密钥卷挂载（权限 600） | 仅该服务进程 / 密钥管理员 |
| **CEK** | 每次随机生成，不保存 | 同左，随令牌走，用完即弃 | 无需持久化 |
| **共享密钥（dir 模式）** | 代码里写死一个演示值 | Vault / KMS / 配置中心加密下发 | 仅签发方与消费方 |
| **口令/证书** | 不入库 | 密钥管理系统 + 定期轮换 | 最小授权 |

### 四种存储方式，按安全等级排序

**🥇 KMS / HSM（推荐）**
密钥**永远不出**密钥服务。你的代码只调用"解密"接口：

```
代码：请用 kms://alias/jwe-key-2026 解开这段密文
KMS ：（内部完成 RSA/AES 运算）返回明文给你
```

好处：即使服务器被入侵，攻击者拿不到密钥本体，只能"借用"解密权限（还能被审计和限流）。

**🥈 容器密钥卷 / 文件挂载**
Kubernetes Secret、Docker secret 挂载成文件，权限 `600`（只有属主可读）：

```bash
chmod 600 /run/secrets/jwe-private.pem
chown app:app /run/secrets/jwe-private.pem
```

**🥉 环境变量**
比硬编码好一点，但注意：环境变量会被 `ps`、崩溃转储、日志、子进程继承泄露，**只能算"及格线"**。

**❌ 绝对不要**
- 写进 Git 仓库（哪怕后来删了，历史记录还在）；
- 写进前端代码 / 移动 App / 小程序（打包即可反编译）；
- 写进日志、异常堆栈、监控上报；
- 写在文档、聊天记录、工单里（Demo8 里的密钥是每次启动随机生成的，正是为了避免"被复制走"）。

### 代码里到底该写什么？

**只写"引用"，不写"密钥本体"**：

```js
// ✅ 正确：只写别名，真实密钥在 KMS 里
const privateKeyRef = 'kms://alias/jwe-key-2026';

// ✅ 正确：只写密钥编号，具体密钥由密钥环根据 kid 提供
const header = { alg: 'RSA-OAEP-256', enc: 'A256GCM', kid: 'demo-key' };

// ❌ 错误：把私钥贴进代码
const privateKey = '-----BEGIN PRIVATE KEY-----\nMIIEvQIBADANBg...';
```

### 轮换（Rotation）：密钥也要"定期换锁"

密钥用久了必须换，但换的姿势不对会**全员掉线**。正确顺序：

| 阶段 | 动作 | 目的 |
|------|------|------|
| ① 发布 | 新密钥对生成，**新旧公钥同时**发布到 JWKS | 让所有验证方都能拿到新公钥 |
| ② 双签/双解 | 新令牌用新 `kid` 签发；**旧私钥仍保留用于解密** | 过渡期内旧令牌还能用 |
| ③ 切流 | 观察一段时间（≥ 令牌最长有效期） | 确认没有旧令牌在流通 |
| ④ 下线 | 移除旧公钥与旧私钥 | 完成轮换 |

配套要求：
- Header 必须带 `kid`，否则接收方不知道该用哪把钥匙；
- 权限最小化：能解密的服务才给它私钥，能加密的服务只给公钥；
- 审计：记录"谁在什么时候调用了哪把密钥"，异常调用要告警。

## 9.9 哪些密钥可以传输？一张判定表

这是新手最容易搞混的地方：**"加密"不等于"什么都能传"。**

| 东西 | 能否传输 | 传输方式 | 说明 |
|------|---------|---------|------|
| **公钥** | ✅ 放心传 | JWKS 接口、配置文件、甚至贴在官网上 | 它本来就是为了公开而设计的 |
| **私钥** | ❌ **绝不** | 不传。只在使用地生成或导入 | 一旦出现在网络/日志里，等于全部作废 |
| **共享密钥（dir 模式）** | ⚠️ 只能"安全预分发" | Vault / KMS / 配置中心加密下发、离线导入 | **绝不能用令牌自己带着走** |
| **一次性 CEK** | ✅ 可以传 | 必须放在 `EncryptedKey` 段（被公钥加密） | 裸传 CEK = 把钥匙和箱子一起寄 |
| **IV** | ✅ 可以传 | 明文第 3 段 | 不需要保密，但**同一密钥下绝不重复** |
| **Tag** | ✅ 可以传 | 明文第 5 段 | 它就是给接收方验的 |
| **Header** | ✅ 可以传 | 明文第 1 段 | 所以别把秘密写进 Header |
| **用户密码** | ❌ 不该传 | 走 HTTPS 提交一次，服务端只存哈希 | JWE 不是用来传密码的 |

### 四种"把钥匙送到对方手里"的方式

| 方式 | 适用 | 风险 |
|------|------|------|
| **公钥加密包裹**（JWE 的 `RSA-OAEP-256`） | 跨系统、跨组织 | 无（私钥不出门） |
| **密钥协商**（`ECDH-ES`） | 双方各有密钥对，协商出 CEK | 实现复杂度稍高 |
| **共享密钥预分发**（`dir`） | 同一信任域内部 | 分发渠道必须可信；谁有密钥谁就能解密+伪造 |
| **密钥管理服务取用** | 云上服务 | 需要网络与授权配置 |

### 三个典型错误（血泪案例）

1. **把 `dir` 的共享密钥写进 JWT 的 payload 里发给对方** —— 等于把钥匙和箱子一起快递，全程白干；
2. **把私钥放进前端**（以为是"客户端解密"）—— 前端代码可被任何人打开，密钥即刻公开；
3. **同一个 IV 重复使用**（比如写死一个 `000000000000`）—— GCM 的安全性直接崩塌，
   攻击者甚至不需要私钥就能恢复明文。

## 9.10 六个高频误解，一次澄清

**Q1：JWE 是不是"用私钥加密、公钥解密"？**
不是。加密永远是"**公钥加密、私钥解密**"。"私钥加密、公钥验证"叫**签名**（JWS）。
两者方向相反，别混。

**Q2：发证中心和资料库是不是都要有私钥？**
只有**接收方（资料库）**有私钥。发证中心只需要对方的**公钥**。
所以"私钥只有双方知道"这个说法本身就不成立——私钥只有一方知道。

**Q3：公钥泄露了会不会有危险？**
不会。公钥的作用就是"让任何人都能给你加密"。真正危险的是私钥泄露。

**Q4：JWE 一定要用 RSA 吗？**
不。也可以用 `ECDH-ES`（协商）或 `dir`（共享对称密钥）。
RSA 只是最通用、最好理解的一种。

**Q5：用了 JWE 就不用 HTTPS 了吗？**
不行。JWE 保护的是"令牌在**存储、转发、日志**中的机密性"，
但请求本身（URL、Header、响应）仍需要 TLS 保护，否则攻击者可以直接改响应、劫持会话。

**Q6：JWE 能防止伪造吗？**
只能防"改"（Tag 校验），不能防"伪造来源"。
因为公钥是公开的，任何拿到公钥的人都能造出一个"格式合法"的 JWE。
要证明"是谁签发的"，必须再加一层签名（见 9.14）。

## 9.11 两组算法：alg 管钥匙，enc 管内容

JWE 的 Header 里**必须同时出现** `alg` 和 `enc`，这是它和 JWS 最大的识别特征。

### enc：内容加密算法（对称，速度快）

| 值 | 说明 | 建议 |
|----|------|------|
| `A256GCM` | AES-256-GCM，带认证标签 | ✅ 首选，现代默认 |
| `A128GCM` / `A192GCM` | 同上，密钥更短 | 合规要求时用 |
| `A128CBC-HS256` | AES-CBC + HMAC，两把密钥 | 老系统兼容用，新项目别选 |

### alg：密钥管理算法（怎么把 CEK 送到对方手里）

| 值 | 机制 | 适用场景 | 私钥/共享密钥在谁手里 |
|----|------|---------|---------------------|
| `RSA-OAEP-256` | 用接收方 RSA 公钥加密 CEK | 跨系统、跨组织 | 只有接收方有私钥 |
| `ECDH-ES` | 双方椭圆曲线协商出 CEK | 移动端/性能敏感 | 双方各有一对密钥 |
| `dir` | 双方**事先共享**一把对称密钥，直接当 CEK | 同一系统内部服务间 | 双方各有同一把共享密钥 |
| `A256KW` | 用共享密钥再"包裹"CEK | 需要频繁轮换 CEK 的场景 | 双方共享 KEK |
| `RSA1_5` | 旧版 RSA 填充 | ❌ 已不推荐（填充预言攻击） | — |

选型口诀：
- **跨组织、要给外部方看** → `RSA-OAEP-256` + `A256GCM`（最通用，最符合"公钥可传、私钥不出门"）
- **自家服务之间** → `dir` + `A256GCM`（最省事，但共享密钥必须安全预分发）
- **性能敏感/移动端** → `ECDH-ES` + `A256GCM`

## 9.12 浓缩版时序图（对照 9.5 / 9.6 的步骤看）

```
签发方（认证中心）                          接收方（资源服务器）
  持有：接收方公钥                            持有：自己的私钥
       │                                          │
       │ ① 造 CEK(32B)                            │
       │ ② 公钥加密 CEK → EncryptedKey(256B)      │
       │ ③ 写 Header → base64url（同时作 AAD）    │
       │ ④ 随机 IV(12B)                           │
       │ ⑤ AES-GCM(CEK, IV, AAD) 加密 → Ciphertext + Tag(16B)
       │ ⑥ 拼 5 段 ──────────────────────────────►│
       │                                          │ ⑦ 私钥解 EncryptedKey → CEK
       │                                          │ ⑧ AES-GCM 解密 + 校验 Tag
       │                                          │ ⑨ 校验 exp / aud / scope
```

关键点：**加密用公钥（可以公开），解密用私钥（绝不外泄）**。
所以"谁来加密"并不重要，重要的是"只有谁能在解密后读到内容"。

## 9.13 GCM 的两个安全细节：Tag 与 AAD

**① Tag（认证标签）**
AES-GCM 是 AEAD 算法，解密时会校验 Tag：
- 密文被改一个字节 → Tag 校验失败 → **抛异常，拒绝返回明文**；
- 这比"解密出乱码"安全得多，因为程序不会误把垃圾当作有效数据。

Demo8 的"篡改密文试试"按钮做的就是这个实验。

**② AAD（附加认证数据）**
Demo8 把 `BASE64URL(Header)` 作为 AAD 绑定进加密计算：

```js
cipher.setAAD(Buffer.from(headerB64, 'ascii'));
```

这样 Header 也受 Tag 保护。否则攻击者可以**换头攻击**：
把 `alg` 从 `RSA-OAEP-256` 改成别的东西、或者换掉 `kid`，诱导对方用错误密钥解密。

> 教训：JWE 的 Header 不是"随便贴的标签"，它必须参与完整性校验。

## 9.14 既有签名又要保密：嵌套令牌

JWE 只保证"看不见"，但接收方**无法确认这封信是谁写的**——
因为公钥是公开的，任何人都能拿它加密一段内容发给你。

如果你的场景同时需要"别人不能看"+"能验证是我签发的"，就做**嵌套**：

| 顺序 | 组成 | 说明 |
|------|------|------|
| **先签后加密**（sign-then-encrypt） | `JWE(JWS(payload))` | ✅ 推荐：先签明文字段，再把整个 JWT 加密。接收方先解密、再验签 |
| 先加密后签名（encrypt-then-sign） | `JWS(JWE(payload))` | 密文可见、签名公开，隐藏不了"有令牌在传"这一事实 |

实现上很直观：把 JWS 的紧凑串当作 JWE 的 payload（`cty: "JWT"` 就是标记这件事）。

**OIDC 里也有它的身影**：规范允许 `id_token` 直接下发成 JWE（5 段），
认证中心的 JWKS 里会额外提供 `use: "enc"` 的加密公钥，客户端用对应私钥解密后再验签。

## 9.15 工程落地清单（踩坑高发区）

- **密钥保管**：私钥/对称密钥放 KMS、HSM 或密钥管理服务，绝不写进代码仓库（详见 9.8）；
- **谁能传谁不能传**：公钥随便发，私钥绝不传，共享密钥只能预分发（详见 9.9）；
- **kid + 轮换**：Header 里带 `kid`，密钥按"发新公钥 → 双解过渡 → 下线旧钥"的顺序轮换；
- **IV 绝不复用**：同一把 CEK 下复用 IV 会直接击穿 GCM 安全性，必须每次随机；
- **算法白名单**：解密时校验 `alg`/`enc` 在允许列表内，禁止 `none`、拒绝 `RSA1_5`；
- **体积与性能**：RSA-2048 加密 + base64 会让令牌膨胀（几百字节起），放 Cookie/Header 时注意 4KB 限制；
- **它不能替代 TLS**：JWE 保护的是"令牌本身在存储、转发、日志中的机密性"，链路安全仍靠 HTTPS；
- **仍要短时效 + 吊销机制**：加密不等于"永久安全"，泄露的 JWE 只要能解密就一直是有效凭证；
- **别忘了审计**：解密失败（Tag 校验错误）应记日志并告警，这往往意味着有人在篡改或试探。

## 9.17 本章小结

- JWT 默认是**签名**（JWS），base64 不是加密，内容人人可读；
- 令牌里要放敏感信息时，用 **JWE** 加密，格式为 5 段：Header / EncryptedKey / IV / Ciphertext / Tag；
- JWE 采用**混合加密**：非对称算法送 CEK，对称算法（AES-GCM）加密数据；
- **公钥可传、私钥不出门、CEK 一次性、IV 每次换**——记住这 16 个字就不会踩大坑；
- 密钥保管（KMS/HSM）与轮换（kid）比算法选择更容易出事，工程上要当作一等公民对待；
- 需要"既保密又能验明出处"时，用 **先签后加密** 的嵌套令牌。
